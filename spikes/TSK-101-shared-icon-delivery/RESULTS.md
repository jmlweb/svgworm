# TSK-101 spike: one source of truth for the Icon delivery logic

Question (PR #14 review, TSK-092): the manifest types and the `use` / `img` / `mask` delivery logic live in four places, `createIcon` in `@svgworm/react` and the `Icon.astro`, `Icon.vue` and `Icon.svelte` templates in `packages/svgworm/src/cli/init/plan.ts`. Is one shared, dependency-free implementation worth it?

## Method

1. Render the three templates and the two loader templates with the current `plan.ts` for a fixed path pair (`src/components/Icon.<ext>`, `src/svgworm`). `src/measure.ts` does it: `node spikes/TSK-101-shared-icon-delivery/src/measure.ts <outDir>` from the repository root writes the rendered files to `<outDir>`, for a before/after `diff -r`.
2. The same script trims each line of the template output and of `packages/react/src/create-icon.tsx`, drops blank lines, de-duplicates them, and intersects the sets. This counts the lines that are literally shared.
3. Read each renderer and sort its logic into "pure, framework-free" and "bound to the framework".
4. Check each option against the package rules (ADR-0008: `@svgworm/react` may not import `svgworm`), the output contract (`docs/output-contract.md`) and how `init` writes files (once, owned by the user afterwards).

## Results (2026-11-09)

### How much is shared

| Set | Distinct non-blank lines |
|-----|-------------------------:|
| `Icon.astro` | 136 |
| `Icon.vue` | 109 |
| `Icon.svelte` | 118 |
| `create-icon.tsx` | 153 |
| Common to the three templates | 43 |
| Common to all four | 25 |

The 25 lines common to all four are the manifest type declarations (about half), markup and punctuation fragments (`{`, `};`, `/>`, `<img`, `<svg`, `</svg>`, `focusable="false"`), `if (!file) {`, and one line of the a11y choice (`? ({ 'aria-hidden': true } as const)`). Apart from that one ternary line, each renderer writes the delivery logic in its own idiom.

The 43 lines common to the three templates add the version check (identical in Astro and Vue, wrapped differently in Svelte) and parts of `fileUrl`.

### What a shared helper could hold

- **Pure, framework-free:** the version check, the own-property icon lookup, `fileUrl` (stack URL, or `#id` for a version 2 sprite), the viewBox size (ADR-0030), the `aria-hidden` / `role="img"` choice, and the mask style string. About 40 lines.
- **Bound to the framework, no helper removes it:**
  - reactivity: `computed` in Vue, `$derived` in Svelte, none in Astro and React;
  - attribute spreading and order: `{...rest}` in JSX, `v-bind` with `inheritAttrs: false` in Vue, `{...rest}` in Svelte;
  - style: React takes an object, Astro serializes an object or a string itself (its `UNITLESS` table), Vue merges an array, Svelte takes a string;
  - the markup of the three deliveries and the `<title>` child.

### The options

1. **A dependency-free helper generated into `moduleDir`** (for example `delivery.js` next to `icons.js`).
   - It is a new generated file, so an output-contract change with a new ADR, a semver note, new determinism and snapshot coverage, and one more file in every project.
   - `@svgworm/react` cannot use it. The package is published and may not import `svgworm` (ADR-0008), and it cannot import a file from the user's `moduleDir`. Sharing would need a new `createIcon(manifest, helper)` API. So it gives two sources (React and the helper), not one.
   - It couples files with different lifetimes. `svgworm build` rewrites `moduleDir` on every run, but `init` writes `Icon.*` once and the user owns it afterwards. A helper whose API changes would break an older `Icon.*` on the next build, so the helper would need its own versioned API.
   - It removes about 40 pure lines from each template, but not the framework-bound half.
2. **A shared template fragment in `plan.ts`.** The pattern exists: `LOADER_TYPES` and `LOADERS_FROM_MANIFEST` with `indent()` (ADR-0036). No contract change and no new file. It removes literal copies inside `plan.ts` only. React keeps its copy. Only the manifest types block is byte-identical in the three templates; the version check and `fileUrl` differ in wrapping and in how they reach the icon (`icon`, `icon.value`, `props.name`), so sharing them changes the generated bytes.
3. **Keep the duplication**, guarded by the conformance tests in `apps/site` (Astro) and `tests/conformance` (Vue, Svelte). They render each template next to `createIcon` from one fixture manifest and fail on any markup difference.

### Trial of option 2

The manifest types block is now one `ICON_MANIFEST_TYPES` constant in `plan.ts`, used by the three templates (indented for Svelte). The generated `Icon.astro`, `Icon.vue`, `Icon.svelte` and both loader components are byte-identical before and after (`diff -r` of the rendered output: no difference). The conformance tests pass unchanged.

## Conclusion

Option 1 does not reach the goal: React cannot read the helper without an API change, and it adds a contract surface that couples build output to user-owned files. The delivery logic that differs between renderers is mostly framework-bound, so even a helper leaves four renderers to keep in step. Keep the four renderers, with the conformance tests as the drift guard, and share only the byte-identical manifest types inside `plan.ts`. Decision: [ADR-0037](../../docs/adr/0037-keep-per-framework-icon-renderers-guarded-by-conformance-tests.md).
