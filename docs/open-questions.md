# Open questions

Each question maps to a backlog task. When an ADR resolves one, mark it ✅ with a link.

## Rendering and browsers

- ✅ **Q-01** Do gradients, masks, clipPath, filters, and `<style>` inside `<symbol>` render correctly through an **external** `<use href="file.svg#id">` in current Chromium, Firefox, and WebKit? If not, which features need a fallback? → TSK-002. Answered by [ADR-0006](adr/0006-per-icon-delivery-external-use-and-svg-stack.md): no. WebKit resolves no `url(#…)` reference (gradient, clipPath, mask, filter) in an external sprite, and Firefox fails a mask containing `<use>`. Icons with references are delivered from an SVG stack (`<img>`, or a CSS mask for mono)
- ✅ **Q-02** Cross-origin sprites (assets on a CDN domain): which workaround should we recommend? Same-origin proxy, inline fallback, or fetch-and-inject (which costs JS)? → TSK-002. Constraint confirmed by [ADR-0006](adr/0006-per-icon-delivery-external-use-and-svg-stack.md): all three engines block cross-origin `<use>`, even with CORS headers. v0.1 documents same-origin as required, and no workaround is prototyped (TSK-014). Workaround choice stays open post-v0.1; [ADR-0010](adr/0010-sprite-url-delivery-generated-module-and-public-path.md) enforces the constraint: a cross-origin or absolute `publicPath` exits with code 2. Answered by [ADR-0027](adr/0027-opt-in-cross-origin-sprites-through-an-injecting-loader.md): a same-origin proxy is the documented zero-JS option, the inline sprite was rejected by [ADR-0024](adr/0024-no-inline-sprite-output.md), and `crossOrigin: "inject"` opts into a hashed loader that fetches the sprite with CORS + SRI and injects it (54/54 browser cases in the TSK-067 spike)
- ✅ **Q-03** Is `viewBox` on `<symbol>` enough for sizing in all browsers, or does the consumer `<svg>` also need it? → TSK-002. Answered by [ADR-0006](adr/0006-per-icon-delivery-external-use-and-svg-stack.md): the symbol's `viewBox` is enough in all three engines. On the consumer it is optional; when set, it carries only the size, never the icon's origin ([ADR-0030](adr/0030-consumer-viewbox-keeps-only-the-size.md))
- ✅ **Q-04** How are `<style>` blocks kept from leaking between icons in a shared sprite (and into the page when inline)? Inline to attributes, prefix class names, reject what can't be scoped? → TSK-002, TSK-003. Partly answered by [ADR-0004](adr/0004-per-icon-color-classification.md): inline every rule, error on any `<style>` left over (all 929 corpus cases inlined). Inline-sprite leakage is still open (TSK-022), deferred to post-v0.1 (ADR-0005). Browser side answered by [ADR-0006](adr/0006-per-icon-delivery-external-use-and-svg-stack.md): a raw `<style>` in an external sprite leaks across symbols in Chromium and is ignored by Firefox and WebKit, so inlining is required. Inline sprites leak `<style>` into the page in all three engines. Closed by [ADR-0024](adr/0024-no-inline-sprite-output.md): there is no inline mode, and the sprite holds no `<style>` anyway
- ✅ **Q-05** If some icons must be inlined as a fallback (Q-01), how does the manifest tell adapters which delivery each icon uses? → TSK-002, TSK-008 Deferred to post-v0.1 with inline fallback (ADR-0005). Partly brought back into v0.1 by [ADR-0006](adr/0006-per-icon-delivery-external-use-and-svg-stack.md): a per-icon `delivery: use | img | mask` field plus a stack URL, with no inline delivery. Field names go to TSK-004. Answered for v0.1 by [ADR-0010](adr/0010-sprite-url-delivery-generated-module-and-public-path.md): `icons.<name>.delivery` plus `sprites.<group>.sprite` and `sprites.<group>.stack`, each `{ file, url }`. Inline delivery was rejected by [ADR-0024](adr/0024-no-inline-sprite-output.md)
- ✅ **Q-06** Icon without a `viewBox`: error, or derive one from `width`/`height`? (R-23) → TSK-002. Answered by [ADR-0006](adr/0006-per-icon-delivery-external-use-and-svg-stack.md): derive `0 0 W H` from plain-number or `px` `width`/`height` and list it in the CLI report. Error otherwise

## Color

- ✅ **Q-10** Which heuristic classifies an icon as mono, stroke, or multicolor reliably? → TSK-003. Answered by [ADR-0004](adr/0004-per-icon-color-classification.md): two classes, mono and multicolor, 99.98% on 31k icons
- ✅ **Q-11** How should `currentColor` be applied: on the root, or rewritten on each element? What about icons that mix fill and stroke? → TSK-003. Answered by [ADR-0004](adr/0004-per-icon-color-classification.md): per element, root only for the default fill, masks frozen
- ✅ **Q-12** Should a CSS custom-property mode (`--icon-color-1`, …) exist for multicolor theming? → TSK-026. Deferred past v1 by [ADR-0004](adr/0004-per-icon-color-classification.md) and to post-v0.1 by ADR-0005. Answered by [ADR-0026](adr/0026-no-generated-css-variable-color-mode.md): no generated mode. Author-written `var(--name, fallback)` paints are kept (ADR-0013) and theme through the external sprite in all three engines; generated slot numbers would mean nothing across icons

## Delivery and integration

- ✅ **Q-20** How does the hashed sprite URL reach the app without a bundler plugin? (generated module with constants, base-path config) → TSK-004. Answered by [ADR-0010](adr/0010-sprite-url-delivery-generated-module-and-public-path.md): the CLI writes the hashed files to `outDir` (default `public/icons`). It also generates `icons.js` + `icons.d.ts` and `manifest.json`, which hold the final URLs built from a configured `publicPath` (default `/icons`; it must start with `/` and include any app base path). There is no bundler import and no runtime fetch
- ✅ **Q-21** How do Next.js App Router, Vite, Astro, and plain HTML each serve the output dir? Should we document recipes, add adapter helpers, or both? → TSK-004 Next.js and plain HTML in v0.1; Vite and Astro deferred to post-v0.1 (ADR-0005). Next.js and plain HTML answered by [ADR-0010](adr/0010-sprite-url-delivery-generated-module-and-public-path.md), with recipes and no adapter helpers. Next: the defaults, `prebuild`, a `headers()` immutable-cache rule, and `publicPath` that includes `basePath`. Plain HTML: serve `outDir` same-origin and read `manifest.json` in the template step. Astro answered by [ADR-0017](adr/0017-astro-support-via-generated-icon-astro.md) (a generated `Icon.astro`; `publicPath` must include `base`). Vite answered by TSK-024: a recipe on the site ([vite.md](../apps/site/src/content/docs/vite.md)), verified by `examples/vite-react` (`pnpm example:vite:check`, with and without `base`)
- ✅ **Q-22** Should sprites be split by namespace, by explicit config groups, or both? Is there a default size limit? → TSK-021. Answered by [ADR-0023](adr/0023-several-sprites-through-one-config-per-sprite.md): neither, yet. Several sprites are one config per sprite (own `outDir`, `publicPath`, `moduleDir`), documented in the config reference; no size limit. Built-in groups can come later without breaking adapters, because each icon already names its group
- ✅ **Q-23** Should the sprite be preloaded (`<link rel="preload">`)? Is that a recommendation, or does an adapter helper emit it? → TSK-039. Answered by [ADR-0019](adr/0019-sprite-preload-not-recommended.md): neither. The `<use>` fetch is `same-origin` mode, which no preload can match, so WebKit (Playwright WebKit 26; real Safari not checked) downloads the sprite twice when a preload is still in flight (and every engine does without a long cache). No helper; the docs will advise against preloading the sprite (TSK-040)
- ✅ **Q-24** Sprite file naming scheme and content-hash length → TSK-004. Answered by [ADR-0010](adr/0010-sprite-url-delivery-generated-module-and-public-path.md): `<group>.<hash>.svg` and `<group>.stack.<hash>.svg`, with the first 8 lowercase hex characters of SHA-256 over the emitted bytes. v0.1 has one group, `icons`
- ✅ **Q-25** Inline sprite output form: raw SVG string, framework component, or both? → TSK-022. Answered by [ADR-0024](adr/0024-no-inline-sprite-output.md): neither. Measured in the Next.js example, an inline sprite costs 2.26 times its size on every HTML response (HTML plus RSC payload), against one year-cached request

## Types and naming

- ✅ **Q-30** Type-checking performance with 5,000+ names: union, `as const` array, or a template-literal approach? → TSK-005. Answered by [ADR-0014](adr/0014-icon-name-type-shape.md): the plain union stays for every size. 20,000 names check in 0.14 s (TS 6) and 0.05 s (TS 7); the `as const` tuple is the slowest shape and the template shape buys nothing but a smaller file
- ✅ **Q-31** Namespace separator and normalization rules (see output-contract) → TSK-006. Answered by [ADR-0007](adr/0007-icon-naming-and-collision-policy.md): `/` separator, NFC + lowercase names, a separate ASCII symbol id (`social/github` → `i-social--github`). Open items with defaults taken are listed in the ADR. Re-examined after dogfooding by [ADR-0021](adr/0021-no-camel-case-splitting-warn-when-case-carried-meaning.md): still no camelCase splitting, plus a `name/case-folded` warning with the suggested file name.
- ✅ **Q-32** Collision policy: always error, or allow an alias map? → TSK-006 Collisions are always an error in v0.1; alias map deferred to post-v0.1 (ADR-0005). Answered for v0.1 by [ADR-0007](adr/0007-icon-naming-and-collision-policy.md): an error that lists every file; alias map is TSK-025. Alias map rejected by [ADR-0025](adr/0025-no-alias-map-for-icon-names.md): rename the file or `exclude` a package file; a per-source prefix (ADR-0020) is the follow-up if two packages collide.

## Tooling (decided only through ADRs after the spikes)

- ✅ **Q-40** Runtime and build tool, test runner, SVG parser and optimizer, CLI framework, config format → TSK-009. Answered by [ADR-0008](adr/0008-tech-stack-and-package-layout.md): Node `^22.20 || >=24.11`, TypeScript 6, `tsc`, Vitest 5, svgo 4, `node:util.parseArgs` + @clack/prompts, `svgworm.config.json` validated with zod
- ✅ **Q-41** Monorepo (core + adapters as separate packages) vs a single package with subpath exports → TSK-009. Answered by [ADR-0008](adr/0008-tech-stack-and-package-layout.md): pnpm workspace with `svgworm` (core + CLI) and a zero-dependency `@svgworm/react`
- ✅ **Q-42** Watch mode implementation and incremental cache → TSK-009, TSK-023. Watch answered by [ADR-0008](adr/0008-tech-stack-and-package-layout.md): recursive `fs.watch` with a debounced rebuild. Incremental part answered by [ADR-0015](adr/0015-incremental-watch-transform-cache.md): an in-memory per-icon transform cache keyed by content, so a rebuild after one change takes about 10 ms for 1,000 icons instead of 850 ms
